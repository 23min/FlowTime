FlowTime Restart Blueprint

Should FlowTime start over with clean specs and a Rust rewrite, and if so, what should the new system look like? This page gives a recommendation, the target architecture, what crosses over from the current repository, and the order of work. Facts about today's repository come from the measurements in the Field Guide; everything about the new system is a proposal.

Decided 2026-10-17: seeded restart, in a new repository, with CUE contracts and verifier-kit in from the start, and an oracle built from closed forms, laws and a reference evaluator, with worked examples stored as data files.   • The weight is everywhere else. About 79,000 lines of C#, 62,000 lines of C# tests and 813,000 words of docs and plans, much of it describing a system the code no longer matches. Working in place, every step must keep those paths working or delete them first.
  • Nothing forces compatibility. There are no users; the consolidation proposal already says so (P8).

Proposal

The architecture: one pure core, thin everything else

One Cargo workspace. At the bottom is a pure library holding the essence: model types, validation, compilation, bin-by-bin evaluation, derived metrics and invariant checks. It does no file, network or clock access, so every result is a function of its input. Three libraries sit above it: templates, analysis and runs. One binary on top serves the CLI, the HTTP API and the WebSocket session from the same calls. Dependencies point only downward.

Proposal

One run, end to end

A template and its parameter values go in. The templates crate lowers them to a model in which every series is declared once. The core validates and compiles that model once, then evaluates it. The result goes to one of three places: a stored run, the UI's live session, or an analysis loop that re-evaluates the same compiled plan with different constants.

Proposal · needs decisions

The model language

The restart is worth most here. Today's two engines disagree mainly about how a model is written, not about arithmetic. Seven rules settle it:

  1. Every series is declared once, by id: as a row, or as a router's named output. No name is invented by convention. Today Rust creates processing_queue and processing_utilization from a topology node's id, and renaming that node silently renames them.
  2. Anything that computes is a node. That covers const, expr, pmf, the backlog row and router. A split is one router node that lists all its branches; consumers read a branch by name, such as HubRouter.airport. In templates, edge weights and class routes become such a router. Today C# lets a router overwrite placeholder rows declared as expr: "0", and Rust applies edge weights only after evaluation, so they feed nothing downstream.
  3. The topology computes nothing. It names the components, says what kind each one is, labels rows with roles (arrivals, served, servers, service time, capacity, buffer) and carries layout. Derived metrics are outputs addressed by the component, such as Processing.utilization.
  4. Sugar exists only in templates and is lowered in one place: queueDepth: self, edge weights, class shorthands.
  5. Parameters are typed, and each one's class is declared. A value parameter becomes a constant row that formulas name directly and that analysis and the UI override without recompiling. A structural parameter (a bin count, a dispatch period, a telemetry file) is resolved when the template is lowered, on the parsed template, never by replacing text. A check rejects a value parameter wherever a literal is required, such as a grid field or a PULSE period.
  6. Variability is an input. Each arrival stream and each service carries how uneven it is (its coefficient of variation): taken from a PMF, measured from telemetry, or assumed. The core reports a per-bin estimate of the random queue and wait beside the fluid queue.
  7. A service is described by its servers and its service time, per request type. Its capacity follows: servers × bin length ÷ service time. A request's time at the service is its service time plus its wait, so two services with the same capacity can differ widely in latency. At the same capacity of 100 requests a second and a load of 90, one server taking 10 ms gives 100 ms per request, and 100 servers taking 1 s each give about 1,022 ms; a model that knows only capacity reports the same for both.

Variability, today and decided. Today both engines replace a PMF with its average before evaluating: C# fills every bin with the expected value (PmfNode), Rust compiles a PMF to a constant, and generated template models store a PMF as an average shaped by a daily profile. A C# path that samples a PMF per bin (PmfCompiler) has no caller in the application. The only use of a PMF's spread is Rust's Kingman metric, which treats every other series as having none. FlowTime computes no request-time percentiles: the Sim service's /api/v1/series/summarize reports percentiles of a series' per-bin values, and telemetry series can be tagged as percentiles so the UI shows them as such.

Decided 2026-10-17: variability becomes part of the model language now. The first estimate per bin uses standard formulas for the typical line and wait at a given load and variability, including services with several parallel workers. Carrying each queue's spread alongside its average, which also handles recovery after a rush and yields bands and approximate percentiles, can follow. The simulation suite judges both against random runs.

Decided: CUE contracts and verifier-kit are in

How it's verified: one gate, three kinds of check

"Verified" covers three different questions, and no single tool answers all three. CUE contracts check that every file and message crossing a boundary has the right shape. They cannot tell a right queue from a wrong one: a model can pass every schema and still compute nonsense, so the numbers need their own oracle, owned by people. verifier-kit contributes the method and the plumbing: one ./verify that every gate calls, a guard that stops the builder from editing the oracle, spines for the parts that really are state machines, and planted bugs that check the checks.

One rule keeps CUE from becoming a second, unchecked copy of the model rules. The CUE schema is the source of truth for shape, and a Rust test feeds the same valid/ and invalid/ fixtures to the Rust parser. If CUE and Rust disagree on a fixture, the build fails. Without that test the repository would again have two validators drifting apart, which E-0023 spent three milestones removing.

verifier-kit fits part of FlowTime as it is. Its spine covers "lifecycle and permissions only", which suits the session and the run lifecycle but not the arithmetic. For the arithmetic, its design suggests reusing a property-testing library (proptest here) and lists decision tables as designed but not built. FlowTime's numeric oracle could be the first real user of that view.

The harness follows five rules:

  • Every series in expected.csv must exist in the output. A missing series fails; nothing is skipped silently.
  • Values are compared bin by bin within the tolerance. A failure names the example, the series, the first differing bin and both values.
  • Warnings are compared exactly, as a set of node and code.
  • Extra output series are ignored: an example pins only what someone derived.
  • An example is committed only when its closed form, the reference evaluator and your ratification agree. A disagreement, including one with the C# second opinion, is settled in the concept spec first.

The first rule is aimed at a known failure: today's parity test skips every Rust series that has no C# series of the same name, so it never compared a single queue Rust created.

Validation against simulation

Decided 2026-10-17: a small discrete-event simulation suite, run on demand and never a gate, built once the core concepts are specified. It doesn't check FlowTime's code. It checks how good the per-bin flow approximation is, and its findings become stated accuracy limits in the concept spec. It also produces synthetic telemetry with known true parameters, which the telemetry work will need.

The theory: the fluid limit

FlowTime's per-bin recurrence is what queueing theory calls a fluid model. Work is treated as a continuous flow, so a queue grows exactly as fast as arrivals exceed capacity and drains exactly as fast as capacity exceeds arrivals. A real system is random: arrivals come in bursts and service times vary, so its queue follows a random path.

The fluid limit connects the two. Multiply arrivals and capacity by a factor n and divide the random queue by n; as n grows, the result converges to the fluid path, the way an average converges in the law of large numbers. The random wobble around that path grows only like √n, by the central limit theorem, so relative to the flow it shrinks like 1/√n. In one line: queue ≈ n × fluid path + √n × noise.

Where the gap concentrates. A queue can't go below zero, so wherever the fluid path sits at zero, randomness only adds: the average of max(0, X) is larger than max(0, the average of X). At the moment a backlog clears, the queue's accumulated randomness is close to normal, with variance σ² = Σ (arrival rate + service rate) × duration over the busy period, and the average of its positive part is σ/√(2π), about 0.4σ. For the spike, σ² = (30 + 20) × 30 + (10 + 20) × 30 = 2,400 at 1×, so theory predicts 19.5 items still waiting where FlowTime says zero; the simulation shows 21.0. This closed form can be one of the simulation suite's own checks.

At steady load. Below capacity the fluid queue is zero at any load, but a random queue holds ρ/(1 − ρ) items on average, where ρ is arrivals divided by capacity (one server, random arrivals and service times: the M/M/1 queue). The simulation lands on that curve.

Counted in items, that queue does not grow with volume when one server simply gets faster, so at high volume it is small next to the flow. Counted in time it does not shrink: an item spends 1/(1 − ρ) service times in the system at any volume, 10 at a load of 0.9 and 20 at 0.95, and that is what latency targets feel. It grows without bound as load approaches capacity: 9 items at 0.9, 19 at 0.95, 99 at 0.99. That is where the flow model is least reliable. FlowTime's Kingman metric is its tool for that wait, and it needs the variability of arrivals and service as input: today it takes it from PMF nodes and treats constant series as having none. When volume comes from more parallel servers rather than a faster one, a different regime applies (the many-server, or Halfin–Whitt, regime); that is a question for the simulation suite and is not measured here. Tails such as p99 stay outside what a flow model predicts at any volume.

Proposal

Order of work

Usefulness is checked early. The first slice ingests telemetry, replays it with a model derived from it, and shows the result on one page, before templates or a full UI exist. Two sources of telemetry go through the same code: openshift-lab, a small real system that runs load tests and emits metrics and OpenTelemetry traces, and a simulation of it whose true parameters are known. Each step ends on a check a machine can run, and the oracle for each concept exists before its Rust does.

Stage A: data and the first oracle

Needs no new repository.

  1. Run bundle

    In openshift-lab, an export script writes one folder per load-test run: k6's run record, the configuration in force (replicas, pools, timeouts, retries), every span of the run from Tempo, and the Prometheus series for the run's time window. FlowTime owns the bundle's format as a CUE contract.

    Done when a constant-rate baseline and one ramp are exported, both pass the contract, and each bundle's span count matches k6's iteration count.

  2. Simulation of the lab

    A discrete-event simulation, in Python on the oracle side, with the lab's services, worker pools and call order, written from the lab's code and its baseline spans rather than from FlowTime's spec. It writes the same bundle and records its true parameters.

    Done when the simulation at the baseline's rate matches the lab's per-hop latencies within a stated tolerance, and its bundles pass the contract.

  3. The service concept and its oracle

    The concept spec for a service (servers, service time and variability) with its closed forms, laws and 3 to 5 worked examples; the reference evaluator for it; and the simulation suite's first systems, one service and two in series. The C# engine is consulted as a second opinion, and each disagreement is settled in the spec.

    Done when the reference evaluator passes every closed-form property of the concept.

Stage B: the first useful slice

Needs the new repository.

  1. New repository, gate first

    Starts once the next aiwf release is out and verifier-kit is stable enough. Generate the devcontainer with devcontainer-kit (answers below), create the Cargo workspace, run aiwf init, install the CUE recipe, and bring in verifier-kit's ./verify and guard, with the expected files under a guarded path. Move rewrite/ in, and copy the formula layer: evaluator, plan and expression parser. Tag the old repository and archive it read-only, keeping it runnable for second opinions.

    Done when a failing test, a fixture the schema wrongly accepts, and a builder change to an oracle path each fail the pull request.

  2. Ingest and flow accounting

    Read a bundle into binned series per hop, take the call graph and call order from spans, and balance each hop's flow with no model.

    Done when the simulated bundles balance exactly and their call graph equals the simulation's, and every imbalance in the lab's bundles is listed and explained.

  3. Page, telemetry only

    One HTML page that draws the files B1 writes: the topology from the data, a time scrubber and per-hop charts, in SVG, with no framework and no server.

    Done when a browser test opens a bundle's output and scrubbing moves every view.

  4. The service in the engine

    Implement A3's concept, with each service's state shaped for counts by stage and age so that mechanisms can be added later.

    Done when every closed-form property, law and worked example passes, the engine agrees with the reference evaluator, and the simulation suite states the concept's accuracy between 70% and 95% load.

  5. Derive and replay

    Build a model from a bundle: servers from the configuration, service times from spans at low load, demand from the load test. Replay the run and report residuals per hop and bin.

    Done when the parameters derived from simulated bundles match the true ones and their residuals stay within tolerance, and the lab's bundles get residuals reported, largest first.

  6. Page, model and telemetry

    Telemetry as dots, the replay as lines, residuals marked.

    Done when a browser test shows a replay beside its telemetry and the largest residual is marked.

  7. First prediction

    From the baseline alone, predict the lab's knee and the hop that saturates first, committed before the lab's ramp runs (openshift-lab E-0004, M-0014).

    Done when the ramp's result is compared with the committed prediction and the comparison is recorded; a miss names what the model lacks.

  8. An AI describes the system

    A skill reads openshift-lab's code, manifests and configuration and writes the model, citing the file and line behind each value, then validates, evaluates and revises it against the residuals. A cited value counts as configured, an uncited one as assumed.

    Done when its model is compared with B4's derived model and each disagreement is explained: a misreading, configuration that isn't what runs, or a mechanism the configuration doesn't show.

Stage C: incidents, one mechanism each

Each incident is designed in openshift-lab with its settings known, predicted before it runs, then run, replayed and explained. A mechanism's closed forms and simulation checks come before its Rust, and it is accepted when it shrinks the residual on the lab's incident and recovers the true parameters from the simulated one.

  1. Held workers

    A slow dependency holds the receiver's workers for the length of each call.

  2. Timeouts and retries

    A client timeout with retries on the call to encryption, under load.

  3. Wasted work

    The same, where the called service keeps working on calls whose caller gave up: the metastable case. Whether the lab's services keep working after the caller gives up is to be checked.

  4. Counterfactuals

    Replay an incident with one setting changed, predict the outcome, then run that setting in the lab.

    Done when each mechanism passes its closed forms, recovers the simulation's truth and shrinks the lab's residual, and each counterfactual's prediction is compared with the lab's run.

Not in Stages A to C: templates and the template language, the HTTP API and live session, the Svelte UI, sweeps and optimization, request classes, autoscalers and modes, variability levels above 1, and what-ifs computed in the page.

Next: D, more mechanisms

Parallel calls and joins, asynchronous hand-offs and message queues, circuit breakers and other modes, autoscalers, rate limits, caches and batching. Each arrives the way Stage C's do: an incident designed in the lab, its prediction, its replay.

    Decided 2026-10-17: closed-form results per concept as the main oracle, plus one reference evaluator for combinations, trusted only after it passes every closed-form property; worked examples are readable instances of the closed forms.

  6. Simulation for validation

    Decided 2026-10-17: a small suite of standard systems (one queue, two in series, a router, retries with timeouts), run on demand and never a gate; its findings become accuracy limits in the concept spec.

  7. Randomness below capacity

    Decided 2026-10-17: variability is part of the model language; per-bin waiting estimates from standard formulas first, built so that tracking each queue's spread can follow.

  8. What describes a service

    Decided 2026-10-17: its servers and its service time per request type. Its capacity follows from them, and a request's time at the service is its service time plus its wait: at the same capacity and load, one server taking 10 ms answers in 100 ms, and 100 servers taking 1 s answer in about 1,022 ms.

  9. How ambitious the core is

    Decided 2026-10-18: shaped from the start for components that carry state and mechanisms; built one concept at a time, the service first, and each further mechanism added when an incident needs it.

  10. What comes first

    Decided 2026-10-18: a slice that ingests telemetry from openshift-lab and from a simulation of it, replays it with a derived model and shows it on one page. Templates and the full UI follow later; see Order of work.

  11. The oracle's language

    Decided 2026-10-17: Python for the whole oracle side (generators, closed-form properties, reference evaluator, simulation suite). It imports nothing from the engine and reaches it only through the CLI.

  13. The queue form
