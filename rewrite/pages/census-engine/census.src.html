Every request is somewhere

A design for FlowTime's engine. It keeps a census of where every request is and how long it has been there, steps that census forward from the present state, and derives everything it shows from it. Every real loop has a delay, so feedback needs no special machinery. The one hard case is a loop that reacts faster than the step.

Four models The census What depends on what Loops Forward only The design Not settled

The next state comes from the current state, and nothing else.

Time only goes forward. A retry follows its timeout, an autoscaler follows its metric window, and a held worker is freed when the reply arrives. The engine's job is to carry enough state that every loop closes through it, and to take steps short enough for the loops that react fastest.

  • Carried from one step to the next: the census, changes already under way, and what each controller remembers.
  • Computed in a step: the transitions. They are what a wire carries.
  • Derived and never stored: latency, utilization, throughput, queue length.
  • Needs care: a loop that reacts faster than the step.

Figure 2 · the state

The state is a census of requests

Every request is somewhere at every moment: queued, being served, waiting on a call it made, backing off before a retry, done, or failed. The engine's state counts how many requests of each type are in each of those stages, and how long they have been there.

Components are views over that census. The api's workers in use are the requests in the stages that hold an api worker. Pricing's queue is every request, of any type, in the stage "queued at pricing".

Carried to the next step

  • The census: counts by request type, stage and age.
  • Attempt number, deadline left or priority, only where a mechanism reads them. Each one multiplies the cost.
  • Changes under way, such as two pods that are ready at 10:17:30.
  • Controller memory: breaker mode and error window, token bucket level, autoscaler window, the averages they read.
  • Cache warmth, and each stage's spread for the variability levels.

Computed in a step

  • Started, completed, called, replied, timed out, retried, rejected, abandoned.
  • Each as a count for the step, with the ages of what moved.
  • A wire in the picture is the set of transitions between stages that belong to two components.

Derived, never stored

  • Latency: age when a request reaches done.
  • Wait: age when service starts.
  • Utilization: workers held by working or waiting stages, divided by workers.
  • Throughput, error rate, queue length.
  • A checkpoint holds the state only. Everything shown is recomputed from it.

A test for a complete state. If a mechanism needs anything older than the state, the state is missing a delay line. The age of each count is such a delay line. Demographers have modeled populations this way for a long time: arrivals are births, and completions and timeouts are deaths whose rate depends on age. The toy's age-bucket shift is essentially their Leslie matrix.

Figure 3 · dependencies

Three kinds of edge

Information delays belong to the mechanism, not to the step. A load balancer that sends traffic to the shortest queue using queue lengths a few seconds old herds traffic back and forth. That is real behavior, and the model shows it only if its delay is the real one.

Metastable failures live in this nesting. An inner loop has two stable states, healthy and storm. A trigger pushes it across, and nothing outside pushes it back unless an outer loop, such as a breaker opening or load shedding, is built to. In the fourth run of Figure 1, demand falls back to 40 per second at 10:32, and pricing still spends all of its capacity on calls whose callers have left.

The design that follows

What the engine would do

  1. Declare the state per mechanism.

    The census, changes under way, controller memory and spread. Each mechanism in the library says what it carries.

  2. Classify every edge.

    Requests, resources or information. Information edges declare their real delay, and the oracle checks that requests are conserved in every step.

  3. Unroll bounded loops by attempt.

    Retries, redirects and hop limits become stages, so the stages never form a cycle.

  4. Choose the step per group of loops.

    From how fast each group reacts, and over time: fine as a surge starts, coarse in quiet hours. Where a stiff loop cannot afford a short step, solve inside the step or use a settled formula, and say so in the output.

  5. Track ages finer than the step.untested

    Shift several age cells per step, so a 2-second timeout is exact with 10-second steps, and unrolled retries land inside the same step. To check: rerun the timeout script with 10-second steps and 1-second age cells; it should match the 1-second run, with a pricing backlog of 620.

The solve inside a step becomes the exception, used only where a loop is both fast and steep. This replaces the two-speed clock on the Building Blocks page: the reporting bin stays what users and telemetry see, while the engine's step is chosen per loop.

Not settled

What this page does not show

  1. How accurate each approximation is.

    The simulation suite (decision 11) runs the same declared system request by request and states the error of each approximation.

  2. The cost at scale.

    Not measured. A day at 1-second steps for 50 components is the case to time, in Rust, once the census exists.

  3. How the engine picks a step on its own.

    Each mechanism would report how fast it reacts in its current state; the rule that turns that into a step is still to be written.

  4. Whether a model like this matches a real system.

    That is a question of evidence, not of the engine; the Derived Models page takes it up.
