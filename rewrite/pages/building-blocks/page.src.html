Building blocks for flows

Components that each have their own behavior, snapped together with calls, with request types sent through them. FlowTime works out what happens to the whole flow, bin by bin, without simulating single requests. That keeps it as quick as a spreadsheet, lets you scrub back and forth in time, and lets it run on telemetry as well as on models.

Like building blocks: pick a piece, set its parts, snap it to the next, then send traffic through.

The pieces come from a fixed library. Each one has parameters, a little state it remembers from one bin to the next, and equations that say what it does in a bin. FlowTime turns a model built from them into one per-bin plan and evaluates it in milliseconds.

  • Components carry servers, a queue, limits, an autoscaler, modes.
  • Calls carry what the caller does: wait or not, fan out, time out, retry, break the circuit.
  • Request types say what flows: each one a call tree, the same shape a trace has.
  • State is richer than one backlog number: the backlog by age, its spread, the replica count, the mode.
What it could look like

One hour of checkout traffic, computed in this page

A toy model of the system in Figure 1. At 10:13 checkout traffic ramps from 40 to 70 per second. Pricing gets three calls per checkout and runs out of servers. Calls that wait longer than 30 seconds time out: the api retries half of them and the other half fail. Email is called without waiting, so its backlog grows and drains later without failing anything. Two switches add mechanisms the plain toy leaves out: the api holding one of its 16 workers for every call it waits on, and pricing still serving calls whose caller has already given up. Drag the time bar or press play, then try the what-if with each switch on and off.

The toy tracks averages, the backlog by age, and a per-bin multi-server waiting estimate (levels 0 to 2 in the table below); a wait is what a call arriving in that bin would see. With the api holding a worker, each bin's holding time is solved inside the bin. The queue then forms at the api's front door, nothing times out, and 32 pricing servers are no longer enough, because the api would need about 31 workers in use at once; in a scratch run, 32 pricing servers with 64 api workers brought latency back to 0.44 s. While the api holds workers, the second switch changes nothing, because no call waits at pricing long enough to time out. Without holding, it turns 16 minutes of partial failure into an outage that is still failing every checkout at 11:00, half an hour after the surge ended. The toy has no timeout at the front door, and its 10-second bins force a 30-second timeout where a real call would give up after about 2 seconds; the Census Engine page measures what a 2-second timeout changes. Every number here comes from this page's script, not from FlowTime; the timer above measures the script on your device.

The pieces, snapped together

There are three kinds of piece. A component is something that does work: a service, a database, a message queue, a team of pickers. A call joins two components and says how the caller behaves. A request type is a kind of traffic with its own path through the components, its own arrival rate over the day, and its own cost at each component.

Today's models describe the flow instead: arrivals at a node, a router splitting them by weights. A weight says a request goes to A or B. It cannot say a request goes to A and B and waits for the slower one, which is what pricing ×3 does. Call trees can, and traces already record them, so a first model can be drawn from a day of traces.

Figure 2

Inside a component

The library holds mechanisms such as these: servers with a service time per request type; a queue with a discipline (first come first served, priority, fair share) and a limit; admission (rate limits, concurrency limits, load shedding); an autoscaler with a lag; modes, where a degraded component runs slower; a cache whose hit ratio cuts calls further down; batching and scheduled dispatch. Each enters the library with its own spec, closed forms and simulation check, the way the queue does in phase 1.

The backlog by age is what makes waits, timeouts and the oldest item computable without following single requests. For a first-come-first-served queue it is exact: the wait of whatever leaves now is the time since that amount of work arrived.

Along a call

The held thread is the coupling that matters most in real systems. When pricing slows down, the api's threads stay busy waiting for it, so the api runs out of threads even though its own work hasn't changed. Layered queueing networks model exactly this. In FlowTime it becomes a small equation solved inside each bin: the api's busy threads depend on pricing's wait, and pricing's wait depends on how much the api sends. Switch it on in the live view at the top to see where the queue moves.

How it stays instant

The Census Engine page refines this picture. The engine carries where every request is and steps it forward from the present state; it needs a solve inside a step only for a loop that reacts faster than the step, and the page measures what that costs.

Each component can be described as simply or as fully as it needs. A component at a low level stays cheap; a low-volume component can afford the full distribution.

Level 3 is accurate exactly where level 4 gets expensive, at high volume: the random part of a queue grows like √n while the flow grows like n, the same result as the fluid-limit chart in the Restart Blueprint.

Past, now, future

Keeping the model aligned in the present needs level 3: the correction weighs the model's own spread against the measurement's noise. The projection then answers the question an on-call engineer asks: "at this rate the queue overflows at 12:10, unless we add 8 servers".

Costs and risks

What it takes

  1. Every mechanism has to be verified.

    Each one needs a spec, closed forms, worked examples and a simulation check before it ships. The library grows one mechanism at a time.

  2. Rich models take work to write.

    Building the first draft from traces has to come early, with defaults for everything traces don't show.

  3. The per-bin solve must always settle.

    Some loops, a retry storm for one, can have two equilibria. The spec has to say which one the engine picks and flag the bin.

  4. Levels 1 to 3 are approximations.

    The simulation suite states how accurate each one is, and the UI shows it.

  5. A library is not a language.

    New behavior enters as a specified mechanism, never as free-form code inside a model.

Decisions

Where this leaves the plan

Decided, decision 14. A service is described by its servers and its service time per request type; its capacity follows from them. Latency is service time plus waiting.

Open: how ambitious the core is. The core's shape is set before the queue spec: what a row holds, the order things are evaluated in, whether there is a solve inside each bin.

  1. Adopt the building blocks and climb the levels one at a time.recommended

    Phase 1 still starts with the queue, as a component with servers, service time and a queue at levels 0 to 2. The core is designed from the start for component state, a mechanism library, call trees and a step chosen per loop (see the Census Engine page), so nothing built now is rebuilt later.

  2. Keep the current plan and add richness after the core ships.

    Smaller now. One number per row and a single evaluation order get baked in, so the rewrite would itself need rewriting.

  3. Specify the whole library before building anything.

    Complete on paper, with no feedback from running code, and the most likely to stall.
