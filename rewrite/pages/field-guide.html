The essence

A spreadsheet for flows

FlowTime evaluates a model over a fixed time grid. Each row is a series with one value per bin. A row is a constant, a formula over other rows in the same bin, or one of three operators that reach back into earlier bins: SHIFT delays a series by k bins, CONV spreads each value over the following bins, and QUEUE carries a backlog forward. The engine fills the sheet one column at a time, left to right, and the same model always produces the same numbers.

Everything else in the repository surrounds this core. Templates and parameters are ways to write the rows. The topology names them. Sweep, sensitivity, goal-seek and optimize refill the sheet with different constants. Two APIs, two CLIs, two UIs and the run folders are ways to look at the result.

Model structure

Rows you write, roles the topology names

The rows know nothing about services. A second block in the model, topology, assigns roles: this series is the arrivals of Processing, that one its served count, its capacity, its queue. From those roles the compiler adds rows of its own: the queue itself, utilization, queue time, latency, cycle time, and checks that raise warnings.

The two layers depend on each other in both directions. In the worked model, the served formula reads a queue row that exists only because the topology asked for it.

Words you'll meet

Time grid
grid: {bins, binSize, binUnit}. Fixed, left-closed bins in UTC. Every value is per bin.
Series
One value per bin. Flows are per-bin totals (arrivals, served); levels are end-of-bin state (queue depth).
Node
A row in nodes[]: const, expr, pmf (collapsed to its expected value), router. C# also accepts a queue here as kind: serviceWithBuffer; Rust does not (see Four ways to write a queue).
Topology node
A service, queue, dlq, sink, router or dependency in topology.nodes[], whose semantics name its rows.
Edge
from: A:served to B:arrivals, with weight, multiplier and lag. Edges feed edge series and conservation checks.
Class
A kind of flow (classes: [{id: Order}]). Series are split per class; DEFAULT when there are none.
Template
A model plus typed parameters, metadata, RNG and ${param} placeholders. The Sim layer turns it into a model by replacing text.
Run
A folder data/runs/<id>/: the model, one CSV per series, run.json, manifest.json.
Analysis modes
Re-evaluate one compiled model with overridden constants: sweep, sensitivity (central difference), goal-seek (bisection), optimize (Nelder–Mead).

From code

What runs today

Two .NET services, two CLIs, two UIs and one Rust binary that runs as a child process. The services never call each other over HTTP. They link the same libraries and share the data/runs/ folder. Color shows which engine computes what.

Measured

Four ways to write a queue

Every model a person wrote in this repository declares its queues in the topology, as a topology node of kind serviceWithBuffer, queue or dlq. The templates mostly add queueDepth: self. No checked-in file puts a queue in nodes[].

The engines differ in how they turn that topology entry into a queue row. The C# engine evaluates nodes[] only, so something must first add a queue node there. Two pieces of C# do that, with different edge cases: Sim's QueueNodeSynthesizer, when it generates a model from a template, and Core's ModelCompiler, on the orchestration path and inside the artifact writer. The Rust compiler creates the queue column itself and rejects a queue node in nodes[]. That makes three implementations of one rule, and the forms they accept overlap only in the simplest case. The Rust engine was built as a structural translation of the C# one; its ten milestones (E-0020) merged over two days in April.

Which form says it best

The essence is a sheet of named rows, and by that measure form A is the clearest engine language. The queue is a row like any other, with a formula that carries state. Every series then has exactly one declaration, a schema can check every reference, and the evaluation graph is complete without reading the topology. The topology is left with labels only: which rows are a service's arrivals, served count and queue. The canonical schema lists serviceWithBuffer as a node kind, and the consolidation proposal's principle P4 says computed series "are all node kinds in the same evaluation graph".

Form D is the clearest authoring language: one line, and no invented names. Form C is the risky one. Names such as processing_queue and processing_utilization come from a naming convention and nothing declares them, so renaming the topology node silently renames them.

A clean split would keep D in templates, lower it to A in one place, and have the engine accept only A, perhaps under a plainer kind name such as queue. The Rust side is closer than it looks. NodeDefinition already parses inflow, outflow, loss, dispatchSchedule and the WIP fields, and the compiler ignores them, reading those settings only from topology nodes. The QueueRecurrence op already exists.

How it got here

The history spans 14 months and 1,415 commits, with three big turns: the UI moved from Blazor to Svelte, evaluation moved partly from C# to Rust, and planning moved from a homegrown framework to aiwf v3. The busiest month, April 2026, produced the Rust engine, the Time Machine, live what-if and the Svelte workbench in about three weeks. Nothing much has moved since June.

Where the weight is

The computing core is small. The Rust engine's parse, compile, evaluate and analyse code is about 3,200 lines without tests. Everything around it is many times larger, and much of it exists twice: two evaluators, two services, two CLIs, two UIs.

Recommendation

A way back in

The core is small, and where both engines can run a model they agree. The confusion comes from three places: two dialects, docs that say Rust replaced C#, and planning prose that outgrew the code. Here is the order I would take, smallest step first. The choices are yours.

  1. Hold two pictures

    The spreadsheet (Fig. 1) and the system map (Fig. 4). Until they are corrected, distrust what README.md, docs/architecture/matrix-engine.md and supported-surfaces.md say about which engine runs.

  2. Make the analysis path tested

    Add cargo test, clippy and FlowTime.TimeMachine.Tests to CI, and make the Rust integration tests fail rather than return when the binary is missing. This is E-0026's first tier and the verification plan's first step.

  3. Pick one model form and use it everywhere

    Decide which queue and router forms the engine accepts (see Which form says it best), then make Sim, C# and Rust agree on it. G-0019 lists the two ways to get there. Until one lands, Rust can't be compared with C# on the real models.

  4. Capture C#, then port concept by concept

    Pin C# outputs for the 12 templates (M-0068's capture), then work through the verification plan's loop, starting with the queue recurrence.

  5. Then the bigger moves

    Single service, parameters as nodes, telemetry ingestion: each waits for a working, compared Rust engine.
