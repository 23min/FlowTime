Derived, not built

FlowTime starts with what happened. It replays an incident from real telemetry, shows where its model disagrees, and grows the model one checked mechanism at a time. It predicts only where that evidence reaches, and every answer lists the assumptions it rests on.

Start with what happened. Predict only where the evidence reaches.

A model written by hand encodes what its author believes. It can look right on a calm day and still be wrong in exactly the conditions a what-if asks about, and nothing marks which parts were ever checked. A model derived from telemetry carries that mark on every part.

  • Post-incident analysis first. An incident holds the stress that calm days never show.
  • Every number has a source: configured, observed, inferred or assumed.
  • Mechanisms are chosen by evidence, and the telemetry that would decide between two is named.
  • Every prediction lists what it rests on that was never checked.
The stance

Why incidents come first

The incident holds the stress.

Timeouts, retries, held workers and backpressure only act under load. A year of calm days cannot show them; one incident can.

Explaining needs no prediction.

A replay feeds the model the demand that actually arrived and compares. The question is what happened, which is a claim the telemetry can check.

Its what-ifs are the safest kind.

"What if the breaker had opened at 10:16" asks about a window the model has just been checked against, under the same conditions.

Each incident adds checked ground.

A mechanism that explained one incident is checked at that load. Later predictions can lean on it there, and only there.

More telemetry helps when it covers more conditions. Another month of calm days adds little. A deploy, a scale-up, a load test or an incident adds a condition the model has not been checked against.

Derived still has a built part. The mechanisms in the library are written by people. Telemetry sets their parameters and chooses between them, and residuals show where something is missing. When nothing in the library explains a residual, a person adds a mechanism, and the next incident checks it.

Built models keep one job: a system that does not exist yet, such as a new service or a launch. Such a model is assumed throughout, and its answers say so.

Figure 3 · a rehearsal

Two models, one incident

A rehearsal with the Building Blocks toy. The toy with the api holding a worker per call plays the real system; its series stand in for telemetry. A first-draft model without holding gets the same demand. Both fit the calm minutes before the surge on latency, and they disagree everywhere else.

Adding the held-worker mechanism makes the residuals vanish here, but only because the second model is the toy that produced the telemetry. On real telemetry it would leave residuals of its own, and the next largest one points to the next mechanism. That is the order the telemetry-analysis spec already sets: rehearse on simulated telemetry with a known answer, then real.

Evidence, weakest first

How a model earns trust

  1. The maths.

    The simulation suite (decision 11) runs the same declared system request by request and states each approximation's error. It checks the engine, not whether the model matches the real system.

  2. A replay it was not fitted on.

    Fit on one week, replay the next with its observed demand, and compare every series per component and bin.

  3. Changes already in the history.

    Deploys, scale-ups, incidents and traffic spikes are free experiments: given the change, did the model show its effect? This matters most, because a what-if is a change.

  4. A prediction written down before an experiment.

    Predict a load test or a chaos experiment, then run it. Nothing earns more trust.
